## Overview

Tarangson uses a **Firestore named database** called `"tarangson"`. The data structure is divided into 3 main groups:

1. **User mapping** -- `userScheduler/{uid}` (links a user to a school)
2. **School data** -- `{schoolId}/...` (school information, roster, academic config)
3. **Timetable data** -- `{schoolId}/timetable/files/{fileId}/...` (timetable files + schedules)

## ER Diagram

```
userScheduler/{uid}
    │
    └──► schoolId ──► {schoolId}/
                         ├── profile
                         ├── subscription
                         ├── address
                         ├── academicDefaults
                         │    ├── teachers/{tid}
                         │    ├── teachers/_settings
                         │    ├── students/{stid}
                         │    ├── students/_settings
                         │    ├── rooms/{rid}
                         │    ├── rooms/_settings
                         │    ├── subjects/{sid}
                         │    └── subjects/_settings
                         │
                         └── timetable/files/{fileId}
                              ├── roster/settings
                              ├── roster/teachers
                              ├── roster/students
                              ├── roster/rooms
                              ├── roster/subjects
                              └── schedules/
                                   ├── setting
                                   ├── teachers/{tid}/{slotKey}
                                   ├── students/{stid}/{slotKey}
                                   └── rooms/{rid}/{slotKey}
```

### Custom Fields System

Every entity type supports custom fields that schools can define themselves:

```typescript
interface CustomFieldDef {
  id: string;
  label: string;
  type: "text" | "number" | "select";
  options?: string[];   // For type "select"
}
```

The `_settings` document in each sub-collection stores the `customFieldDefs` array, while the actual values are stored in the `customFields` map of each entity.

### Roster Sub-documents

Each timetable file contains a snapshot of the roster at the time of creation:

| Path | Content |
|---|---|
| `roster/settings` | `RosterAcademic` -- days, periods, times |
| `roster/teachers` | `Record<string, Teacher>` -- map of teacher data |
| `roster/students` | `Record<string, Student>` |
| `roster/rooms` | `Record<string, Room>` |
| `roster/subjects` | `Record<string, Subject>` |

### Schedule Timeslots (Denormalized)

<Callout type="info">
  Schedule data is **denormalized into 3 collections** (teachers, students, rooms) so that loading each view is fast without cross-collection queries.
</Callout>

**Path pattern:**
```
{schoolId}/timetable/files/{fileId}/schedules/{entityType}/{entityId}/{slotKey}
```

**SlotKey format:** `"{DAY}_{PERIOD}"` e.g., `"MON_1"`, `"WED_5"`

**TimeslotData:**

```typescript
interface TimeslotData {
  subjectId: string;
  teacherId?: string;
  studentId?: string;
  roomId?: string;
  specialPeriods?: SpecialPeriodsInfo | string;
  isPin?: boolean;
}
```

The stored data differs by collection:

| Collection | Stored Fields |
|---|---|
| `schedules/teachers/{tid}/{slotKey}` | `subjectId`, `studentId`, `roomId` |
| `schedules/students/{stid}/{slotKey}` | `subjectId`, `teacherId`, `roomId` |
| `schedules/rooms/{rid}/{slotKey}` | `subjectId`, `teacherId`, `studentId` |

<Callout type="warning">
  Writes must always update all 3 collections simultaneously via `runTransaction` to prevent data inconsistency.
</Callout>
