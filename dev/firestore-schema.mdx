## ภาพรวม

Tarangson ใช้ **Firestore named database** ชื่อ `"tarangson"` โดยโครงสร้างข้อมูลแบ่งเป็น 3 กลุ่มหลัก:

1. **User mapping** -- `userScheduler/{uid}` (ผูก user กับ school)
2. **School data** -- `{schoolId}/...` (ข้อมูลโรงเรียน, roster, academic config)
3. **Timetable data** -- `{schoolId}/timetable/files/{fileId}/...` (ไฟล์ตารางสอน + schedule)

## ER Diagram

```
userScheduler/{uid}
    │
    └──► schoolId ──► {schoolId}/
                         ├── profile
                         ├── subscription
                         ├── address
                         ├── academicDefaults
                         │    ├── teachers/{tid}
                         │    ├── teachers/_settings
                         │    ├── students/{stid}
                         │    ├── students/_settings
                         │    ├── rooms/{rid}
                         │    ├── rooms/_settings
                         │    ├── subjects/{sid}
                         │    └── subjects/_settings
                         │
                         └── timetable/files/{fileId}
                              ├── roster/settings
                              ├── roster/teachers
                              ├── roster/students
                              ├── roster/rooms
                              ├── roster/subjects
                              └── schedules/
                                   ├── setting
                                   ├── teachers/{tid}/{slotKey}
                                   ├── students/{stid}/{slotKey}
                                   └── rooms/{rid}/{slotKey}
```

## Collections & Documents

### `userScheduler/{uid}` -- User-School Mapping

ผูก Firebase Auth UID กับ school ID สำหรับ multi-tenant

```typescript

  schoolId: string;      // ID ของโรงเรียนที่สังกัด

  phone: string;
}
```

### Custom Fields System

ทุก entity type รองรับ custom fields ที่โรงเรียนกำหนดเอง:

```typescript
interface CustomFieldDef {
  id: string;
  label: string;
  type: "text" | "number" | "select";
  options?: string[];   // สำหรับ type "select"
}
```

`_settings` document ในแต่ละ sub-collection เก็บ `customFieldDefs` array ส่วนค่าจริงเก็บใน `customFields` map ของแต่ละ entity

### Roster Sub-documents

แต่ละ timetable file มี snapshot ของ roster ณ ตอนสร้าง:

| Path | Content |
|---|---|
| `roster/settings` | `RosterAcademic` -- วัน, คาบ, เวลา |

| `roster/students` | `Record<string, Student>` |
| `roster/rooms` | `Record<string, Room>` |
| `roster/subjects` | `Record<string, Subject>` |

### Schedule Timeslots (Denormalized)

<Callout type="info">
  ข้อมูล schedule ถูก **denormalize เป็น 3 collections** (teachers, students, rooms) เพื่อให้ load ข้อมูลแต่ละมุมมองได้เร็วโดยไม่ต้อง query ข้าม collection
</Callout>

**Path pattern:**
```
{schoolId}/timetable/files/{fileId}/schedules/{entityType}/{entityId}/{slotKey}
```

**SlotKey format:** `"{DAY}_{PERIOD}"` เช่น `"MON_1"`, `"WED_5"`

**TimeslotData:**

```typescript
interface TimeslotData {
  subjectId: string;
  teacherId?: string;
  studentId?: string;
  roomId?: string;
  specialPeriods?: SpecialPeriodsInfo | string;
  isPin?: boolean;
}
```

ข้อมูลที่เก็บจะแตกต่างกันตาม collection:

| Collection | เก็บอะไร |
|---|---|
| `schedules/teachers/{tid}/{slotKey}` | `subjectId`, `studentId`, `roomId` |
| `schedules/students/{stid}/{slotKey}` | `subjectId`, `teacherId`, `roomId` |
| `schedules/rooms/{rid}/{slotKey}` | `subjectId`, `teacherId`, `studentId` |

<Callout type="warning">
  การ write ต้องเขียนทั้ง 3 collections พร้อมกันผ่าน `runTransaction` เพื่อป้องกัน data inconsistency เสมอ
</Callout>
